# SparkDeck 项目宪法

本文件约束所有规格、设计、代码和验收。冲突时以本文件为准。

## 一、SDD 顺序

任何重要功能依次完成：`Spec → Design → Tasks → Implement → Verify`。

- Spec 明确输入、输出、边界和验收标准。
- Design 明确领域模型、数据流、Port、失败处理和取舍。
- Tasks 必须可独立验证。
- 验收标准不清楚时，不得直接增加生成逻辑。

## 二、产品边界

SparkDeck 是适用于幼儿园全部演示场景的通用 AI PPT 平台，不是某一种课件或家长会模板生成器。

主流程固定为：`基本信息 → 大纲生成与编辑 → 用户确认 → 设计与自动生成 → 在线编辑 → 质量检查 → 导出`。

具体主题、班级、活动和测试案例只能是输入或夹具，不得成为生产代码分支。

## 三、坚决禁止

1. 禁止 `场景/标题/页码/页面角色 → 固定坐标、固定图片槽、固定模板`。
2. 禁止模型输出坐标、CSS、HTML、SVG 或 PPTX 代码进入生产渲染。
3. 禁止每页固定为标题、正文、图片三个槽；页面必须允许多个内容组和多个媒体关系。
4. 禁止在构图候选确定前批量生成图片。
5. 禁止把图片描述、制作说明、占位文案或提示词显示给观众。
6. 禁止把可编辑文字默认画进整页背景图。
7. 禁止背景图自动缩成卡片，或主体图自动升级为背景。
8. 禁止预览与 PPTX 导出使用两套布局事实来源。
9. 禁止自动进行新的付费重试、静默切换模型或整稿重跑。
10. 禁止只凭“能导出、无越界”宣布视觉验收通过。
11. 禁止业务层直接依赖供应商 SDK、数据库、文件系统、Web 框架或渲染库。
12. 禁止复制第三方项目作为产品内核；外部项目仅可作为研究依据，除非用户明确批准引入。

## 四、架构与代码原则

1. 遵循 Clean Architecture：`Domain ← Application ← Adapters/Infrastructure ← Interfaces`，依赖只能向内。
2. 遵循 SOLID：模块保持单一职责；新增模型、存储、渲染器和质量检查器优先通过 Port/Adapter 扩展。
3. 领域协议不包含供应商、数据库、网络、文件路径、CSS 或 PPTX 库类型。
4. AI 负责叙事和设计意图；代码负责约束、求解、评分、渲染和导出。
5. Scene Graph 是预览、编辑、质量检查和 PPTX 导出的唯一事实来源。
6. 所有外部输入和模型输出必须经过 Schema、引用完整性和制作语言校验。
7. 注释只解释重要意图、约束和取舍；禁止用批量注释代替清晰命名和模块边界。
8. `.env` 和密钥不得删除、提交、回显或写死；示例配置不得包含真实密钥。

## 五、完成标准

只有同时满足以下条件才算完成：

- 类型检查、构建、相关单元测试和集成测试通过；
- 全页规则质量检查通过，高风险页进入视觉复核批次；
- 每个生成素材都被最终 Scene Graph 引用，未放置素材调用数为零；
- 标题、正文、形状、图表和图片在 PPTX 中保持独立可编辑；
- 预览与导出的语义指纹一致；
- PPTX 逐页渲染后无空标题、溢出、错误重叠、错误裁剪和制作语言；
- 至少使用三个未写入生产代码的外部 Brief 验证通用性；
- 生产代码中没有新增具体场景判断和页面角色坐标映射。

修改本宪法必须由用户明确提出。
