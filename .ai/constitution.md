# SparkDeck 项目宪法

本文件是所有需求、设计、代码和 AI 操作的最高约束。与其他说明冲突时，以本文件为准。

## 一、SDD 执行顺序

任何功能必须依次完成：

1. `Spec`：明确用户、场景、输入、输出、边界和验收条件。
2. `Design`：明确领域模型、接口、数据流、失败处理和技术取舍。
3. `Tasks`：拆分可独立验证的小任务。
4. `Implement`：只实现已确认范围。
5. `Verify`：用测试和渲染结果验收。

需求或验收条件不清楚时，禁止直接写生成逻辑。

## 二、产品边界

SparkDeck 是适用于幼儿园全部场景的通用 AI PPT 平台，不是某一种课件生成器。

必须支持以下主流程：

`基本信息 → 大纲生成与编辑 → 页面/素材方案 → 自动生成 → 在线预览与局部编辑 → 导出`

## 三、坚决禁止

1. 禁止把任何具体业务场景写死为不可扩展的代码分支。
2. 禁止把页面语义绑定到固定坐标、固定图片槽或唯一版式。
3. 禁止让模型直接生成页面坐标、PPTX代码或逐页渲染代码。
4. 禁止无限重试或失败后静默切换外部服务。
5. 禁止把可编辑文字固化进背景图片。
6. 禁止大纲未经确认就直接生产完整 PPT。
7. 禁止用空标题、空页面、内容缺失、元素溢出或重叠的结果继续导出。
8. 禁止业务层直接依赖具体供应商、数据库、渲染库或 Web 框架。
9. 禁止硬编码密钥、供应商地址和用户数据。
10. 禁止为了赶进度绕过类型检查、契约校验和视觉验收。
11. 禁止未经许可证、维护状态和替换成本评估就引入外部项目或核心依赖。

## 四、强制设计原则

1. 必须遵循整洁架构：`Domain → Application → Adapters/Infrastructure`，依赖只能由外向内。
2. 领域层必须保持纯净，不依赖框架、数据库、网络、文件系统、模型 SDK 或渲染库。
3. 用例通过 Port 表达依赖，由组合根注入 Adapter；禁止在用例内部直接实例化基础设施。
4. 必须遵循 SOLID：
   - `SRP`：一个模块只有一个主要变化原因。
   - `OCP`：新增模型、存储、布局或渲染器以扩展为主，不修改稳定核心。
   - `LSP`：任何 Adapter 都必须满足对应 Port 的契约和测试。
   - `ISP`：接口保持小而专一，禁止万能 Service 或万能 Repository。
   - `DIP`：高层策略只依赖抽象，不依赖具体供应商和工具。
5. 领域规则必须与模型、渲染器、存储和 UI 解耦。
6. 内容语义与渲染坐标必须分离，外部生成结果不能直接成为最终可执行渲染指令。
7. 项目结构数据是唯一事实来源；预览和导出必须来源一致。
8. 可变的外部能力必须可通过 Adapter 替换，不得污染领域模型。
9. 所有外部输入和响应必须经过契约校验；所有错误必须显式处理。
10. 公共契约和领域模型必须有独立测试；基础设施必须通过契约测试验证可替换性。

## 五、完成标准

功能只有同时满足以下条件才算完成：

- 符合已确认 Spec 和验收条件。
- 类型检查、构建和相关测试通过。
- 关键输出通过本地 Schema 与业务规则校验。
- PPT 无空标题、溢出、重叠、缺图和错误裁切。
- 导出内容可编辑，预览与导出一致。
- 没有未授权调用或隐藏重试。
- 没有新增具体场景的硬编码分支。

## 六、变更规则

修改本宪法必须由用户明确提出并确认。任何实现不得通过其他文档、注释或临时决定规避本宪法。
